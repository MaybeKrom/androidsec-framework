MASVS control explanations

These sections are the OWASP MASVS v2 controls, in document order. That set includes every id in rules/owasp_mapping.json. Control names follow the MASVS statements. Severity and CVSS figures are typical ranges for issues in that area. They are not scores assigned by the standard.

The findings table links any value shaped like MASVS-STORAGE-1 to the matching anchor on this page. A rule added to the mapping later links on the next report with no change to the report template. Every id in rules/owasp_mapping.json has a section here.

MASVS-STORAGE-1

The app securely stores sensitive data.

This control covers data the app stores on purpose: passwords, tokens, keys, personal data, and anything else that has to stay confidential. The location can be private app storage or a public folder. Either way, the data has to be protected. Unintentional leaks through backups and logs are MASVS-STORAGE-2.

androidsec maps embedded secrets to this control: cloud keys, API tokens, JWTs, hardcoded passwords, and similar strings shipped inside the package. A secret in the APK is stored where every copy of the app can be read.

Security controls and focus areas

  • Sensitive values encrypted at rest, with the key in the Android Keystore rather than next to the ciphertext.
  • Files and databases created MODE_PRIVATE, not world-readable, and not in a public directory unless the data is meant to be public.
  • No passwords, API keys, private keys, or long-lived tokens in source, resources, assets, or native libraries.
  • Account data kept in a store that the platform protects, and wiped when the user logs out.

Common vulnerabilities and attacks

  • Hardcoded credentials and API keys recovered from classes.dex, strings, or a native library.
  • Plaintext passwords or tokens in SharedPreferences or a SQLite database the app created for that purpose.
  • A private key embedded so the app can decrypt or sign without a server.
  • Sensitive files written to shared external storage as the normal place the app keeps them.

How these issues are usually exploited

The package is unpacked and the string, resource, or native blob is read. A cloud key or bearer token found there is used from anywhere, with no access to a device. A password stored in plaintext preferences is read from a backup, a debuggable process, or a rooted device, then reused against the account.

OWASP Mobile Top 10 (2024)M9 Insecure Data Storage. M1 Improper Credential Usage when the stored value is a password, token, or API key.
Typical severityHigh to Critical for a live credential, cloud key, or private key. Low or Info for a value that does not grant access, such as a documentation IP embedded in the binary.
Suggested CVSS range7.5–9.8 when the secret in the APK works over the network. About 5.5–7.5 when the plaintext store is only readable with local access.
Common CWEsCWE-312 Cleartext Storage of Sensitive Information. CWE-798 Use of Hard-coded Credentials. CWE-522 Insufficiently Protected Credentials. CWE-311 Missing Encryption of Sensitive Data.

MASVS-STORAGE-2

The app prevents leakage of sensitive data.

Some sensitive data is written on purpose. This control is the other case: data that ends up in a backup, a log, the clipboard, external storage, or a screenshot because of how an API works. The developer can usually turn that path off.

Security controls and focus areas

  • android:allowBackup="false", or backup rules that exclude credential and token files, on apps that store secrets.
  • No secrets in Log output, crash reports, or analytics events.
  • App-specific directories instead of world-readable external storage.
  • Clipboard and screenshot exposure limited for screens that show passwords, card numbers, or one-time codes.
  • Careful use of the keyboard cache and WebView form history.

Common vulnerabilities and attacks

  • Insecure data storage: credentials, tokens, or statements written to external storage or to a world-readable file.
  • Backup leakage: adb backup or a device transfer includes the private preferences that hold secrets.
  • Sensitive values written to logcat, which any app with the right access, or a USB host, can read.
  • A password placed in an SMS body, or credentials written to a temporary file that another app or a backup can read.
  • Data left in the clipboard or in a task-switcher screenshot.

How these issues are usually exploited

Someone with local access copies the backup archive or reads the file on shared storage. The app did not offer that file as an API. The leak is a side effect of the default backup flag, a log line, or a path under /sdcard. On a device that allows backup, the archive contains the same private files the app thought were sandboxed.

OWASP Mobile Top 10 (2024)M9 Insecure Data Storage. M6 Inadequate Privacy Controls when the leaked data identifies the user. M1 Improper Credential Usage when the leaked data is a password or token.
Typical severityLow to High. A log of a non-secret path is Low or Info. A backup or external file that contains credentials or session material is High.
Suggested CVSS range4.0–7.5. These issues almost always need local access, so the attack vector is local. The score rises when the file contains a reusable password or token.
Common CWEsCWE-312 Cleartext Storage of Sensitive Information. CWE-921 Storage of Sensitive Data in a Mechanism without Access Control. CWE-532 Insertion of Sensitive Information into Log File. CWE-359 Exposure of Private Personal Information.

MASVS-CRYPTO-1

The app employs current strong cryptography and uses it according to industry best practices.

This control is about the algorithm, the mode, and how the primitive is used. Key generation and key storage are MASVS-CRYPTO-2. External references such as NIST SP 800-57 and SP 800-175B are the usual baseline: a current AEAD mode, a unique IV, and no broken ciphers.

androidsec maps ECB, DES, an embedded private key, and runtime use of the app’s crypto helper to this control. MD5 and SHA-1 used as security hashes are mapped to MASVS-CRYPTO-2 in the current rules. They are still failures of cryptographic practice and belong in the same conversation as this control.

Security controls and focus areas

  • AES-GCM or another current authenticated mode. CBC only with a random IV and a separate integrity check.
  • No DES, 3DES, RC4, or ECB for confidential data.
  • Password storage with a password hashing function, not a fast hash such as MD5 or SHA-1.
  • Library APIs used as documented. No homemade XOR, no “encrypt then forget the MAC”.

Common vulnerabilities and attacks

  • ECB mode, which encrypts identical blocks to identical ciphertext and leaks structure.
  • DES or another short-key cipher that can be brute-forced.
  • A private key shipped in the app and used to decrypt data or to sign requests the server trusts.
  • Hashing a password with MD5 or SHA-1 and treating the digest as a verifier.

How these issues are usually exploited

The transformation is identified from the code or from the ciphertext shape. ECB is confirmed when repeated plaintext blocks repeat in the ciphertext. DES is searched across its small key space. An embedded private key is extracted and used offline against captured ciphertext or to forge a signature. A fast password hash is attacked with a wordlist.

OWASP Mobile Top 10 (2024)M10 Insufficient Cryptography. M1 Improper Credential Usage when the broken primitive protects a password or token.
Typical severityHigh to Critical when the data is a password, token, or message the server trusts. Low when a weak hash is used only as a non-security checksum.
Suggested CVSS range7.0–9.1 when ciphertext or a forged signature can be produced from material in the APK. Lower when the weak algorithm protects data that is already public.
Common CWEsCWE-327 Use of a Broken or Risky Cryptographic Algorithm. CWE-328 Use of Weak Hash. CWE-329 Generation of Predictable IV with CBC Mode. CWE-321 Use of Hard-coded Cryptographic Key when the private key is the embedded secret.

MASVS-CRYPTO-2

The app performs key management according to industry best practices.

A strong cipher still fails if the key is guessable, hardcoded, stored next to the ciphertext, or reused with a fixed IV. This control covers generation, storage, and protection of keys for their whole life. Algorithm choice itself is MASVS-CRYPTO-1. Weak random numbers matter here when they are used to generate a key.

Security controls and focus areas

  • Keys generated with a cryptographically secure RNG and stored in the Android Keystore when the platform can hold them.
  • No key material, key-derivation password, or IV embedded in source, resources, or native libraries.
  • A unique, unpredictable IV for each encryption under the same key. A fixed all-zero IV is not that.
  • Keys kept out of preferences, databases, and logs that sit beside the ciphertext.
  • Rotation and deletion of keys that are no longer needed.

Common vulnerabilities and attacks

  • Hardcoded cryptographic keys and hardcoded credentials in the APK.
  • A static IV, or ECB mode, so identical plaintext blocks encrypt identically.
  • Keys derived from a short or public string, including a value shipped in the same app.
  • java.util.Random or another non-cryptographic generator used where a key or token needs SecureRandom. That is primarily a cryptography-practice failure (MASVS-CRYPTO-1) and is mapped here when it affects key generation.
  • Weak or obsolete algorithms (DES, RC4, homemade XOR) used with those keys. The algorithm finding belongs to MASVS-CRYPTO-1; the key that makes the ciphertext readable belongs here.

How these issues are usually exploited

The key string is recovered from the decompiled app or from its resources. The ciphertext is then read from the app’s private storage, a backup, or a preference file, and decrypted offline. A fixed IV lets an analyst confirm the algorithm with a known plaintext. No interaction with the server is required once both the key and the ciphertext are in hand.

OWASP Mobile Top 10 (2024)M10 Insufficient Cryptography. M1 Improper Credential Usage when the hardcoded secret is a password, token, or API key rather than a cipher key.
Typical severityHigh to Critical when the recovered key decrypts passwords, tokens, or traffic. Low when a predictable generator is used for a value that is not secret.
Suggested CVSS range7.0–9.1 when the key is in the distributed APK and the ciphertext is stored on the device. The attacker needs the ciphertext, so the score depends on whether that file is local-only or already backed up.
Common CWEsCWE-321 Use of Hard-coded Cryptographic Key. CWE-798 Use of Hard-coded Credentials. CWE-329 Generation of Predictable IV with CBC Mode. CWE-330 Use of Insufficiently Random Values. CWE-327 Use of a Broken or Risky Cryptographic Algorithm.

MASVS-AUTH-1

The app uses secure authentication and authorization protocols and follows the relevant best practices.

Most apps send the user to a remote service that decides who they are and what they may do. The decision has to be enforced on that service. The app still has to use the protocol correctly: the right OAuth or session flow, tokens kept out of logs and URLs, and no feature gated only by a flag on the client.

No current androidsec rule maps to this id. The section is here so a later mapping entry links to a real anchor.

Security controls and focus areas

  • Authorization checked on the server for every sensitive request, not only in the UI.
  • A current authentication protocol, with the redirect, state, and token handling that protocol requires.
  • Session tokens stored as sensitive data and sent only over TLS.
  • Account lockout or throttling against repeated password attempts, enforced by the service.

Common vulnerabilities and attacks

  • Broken authorization: the app hides a button, but the API still accepts the call.
  • Password spraying and credential stuffing against a login API that does not throttle.
  • OAuth redirects that an attacker can intercept, or tokens placed in a URL and then in logs.
  • A client-side role flag that a modified app can flip.

How these issues are usually exploited

The attacker calls the API directly, or walks a list of common passwords against many accounts slowly enough to avoid a lockout. A token leaked in a referrer or a log is replayed. A patched client sends an admin action the server never re-checks.

OWASP Mobile Top 10 (2024)M3 Insecure Authentication/Authorization. M1 Improper Credential Usage when tokens or passwords are the thing that leaks.
Typical severityHigh to Critical when another user’s data or actions are reachable. Medium when the flaw is limited to the attacker’s own session.
Suggested CVSS range6.5–9.8. Remote attacks that need no prior account sit at the top. A flaw that still needs a valid login is lower.
Common CWEsCWE-287 Improper Authentication. CWE-306 Missing Authentication for Critical Function. CWE-862 Missing Authorization. CWE-307 Improper Restriction of Excessive Authentication Attempts.

MASVS-AUTH-2

The app performs local authentication securely according to the platform best practices.

Biometrics and an on-device PIN have to be implemented with the platform APIs. A local check that only returns a Boolean the app itself can change does not authenticate anyone. Some apps have no server and rely entirely on this check.

androidsec maps a hardcoded developer login to this control. A client that accepts /devlogin or devadmin is doing that check itself. Anyone who unpacks the package learns the account, and the app never asks a server.

Security controls and focus areas

  • BiometricPrompt with a CryptoObject bound to a Keystore key, so a successful prompt is what unlocks the key.
  • A device credential fallback that uses the platform lock, not a PIN stored in preferences.
  • Failure handling that does not unlock data after a fixed number of local errors the app counts itself.

Common vulnerabilities and attacks

  • A biometric “check” that sets a Boolean the rest of the app trusts. Changing that Boolean skips the prompt.
  • The PIN or its hash stored in preferences next to the data it is supposed to protect.
  • Local-only authentication in front of data that is still readable in storage.

How these issues are usually exploited

On a device the person controls, the method that reports success is changed so it returns success without a fingerprint. If the PIN is in a preference file, that file is read and the check is irrelevant. The data the prompt was meant to protect is then used directly.

OWASP Mobile Top 10 (2024)M3 Insecure Authentication/Authorization. M9 Insecure Data Storage when the PIN or the protected data is readable anyway.
Typical severityHigh when the local check is the only thing in front of secrets or payments. Medium when the server still requires its own login.
Suggested CVSS range4.0–7.5. The attacker is local. The score follows what the bypass reveals.
Common CWEsCWE-287 Improper Authentication. CWE-288 Authentication Bypass Using an Alternate Path. CWE-693 Protection Mechanism Failure.

MASVS-AUTH-3

The app secures sensitive operations with additional authentication.

A transfer, a password change, or a new payee should ask for something beyond the session that is already open. That second step can be a biometric prompt, a PIN, a one-time code, or a confirmation on another channel. It has to be checked by the service that performs the action.

No current androidsec rule maps to this id.

Security controls and focus areas

  • Step-up authentication on payments, password and email changes, and adding a beneficiary.
  • The server rejects the sensitive call when the step-up proof is missing or reused.
  • One-time codes that expire quickly and are not shown in a notification anyone on the lock screen can read.

Common vulnerabilities and attacks

  • The sensitive API trusts the existing session and never asks again.
  • A deep link or a client flag that marks a transaction as already confirmed.
  • One-time codes that can be replayed, or that are brute-forced because they are short and not rate-limited.

How these issues are usually exploited

A stolen session token is enough to move money or change the recovery email, because nothing else is required. Or the client is told to skip the prompt and the server accepts the resulting request. A code intercepted from a notification or an SMS is submitted before the user is.

OWASP Mobile Top 10 (2024)M3 Insecure Authentication/Authorization.
Typical severityHigh to Critical when the missing step-up protects money, account recovery, or personal data.
Suggested CVSS range6.5–8.8. Impact is high and the attacker often already has a session, which keeps the score below an unauthenticated remote compromise.
Common CWEsCWE-306 Missing Authentication for Critical Function. CWE-308 Use of Single-factor Authentication.

MASVS-NETWORK-1

The app secures all network traffic according to the current best practices.

Data on the network has to be encrypted and the remote host has to be authenticated. TLS does both when the app keeps the platform defaults. This control fails when the app allows cleartext, trusts every certificate, or uses a client that skips hostname checks.

Security controls and focus areas

  • HTTPS for every endpoint, including login, updates, and third-party calls made by the app.
  • A network security config that sets cleartextTrafficPermitted="false" and does not add user-installed trust anchors in release builds.
  • No custom TrustManager or HostnameVerifier that accepts any certificate or any hostname.
  • Platform HTTP clients rather than a raw socket that never performs a TLS handshake.

Common vulnerabilities and attacks

  • Cleartext traffic: login or session data sent over HTTP, so anyone on the path can read and change it.
  • A missing network security config on an older target SDK, which leaves cleartext permitted.
  • Certificate validation turned off, so the app accepts an attacker certificate.
  • Certificate pinning bypass is the related attack against MASVS-NETWORK-2 (identity pinning), not against this control. Pinning restricts which certificate authorities are trusted after TLS is already required. A bypass hooks the pinning check so a proxy certificate is accepted. An app can fail NETWORK-1 and never implement pinning at all.

How these issues are usually exploited

On a shared network, a proxy or a rogue access point presents itself as the server. If the app speaks cleartext, the proxy reads the body. If the app trusts all certificates, the proxy terminates TLS with its own certificate and the app continues. A hostname verifier that always returns true lets that certificate claim to be the real host.

OWASP Mobile Top 10 (2024)M5 Insecure Communication.
Typical severityMedium to Critical. Cleartext that carries a password or session token is High or Critical. A missing network security config on an app that already uses HTTPS for every call is often Medium or Info.
Suggested CVSS range5.9–9.1 when credentials or tokens cross a network an attacker can sit on. Adjacent-network attacks are usually lower than a remotely exploitable validation bypass that needs no special position.
Common CWEsCWE-319 Cleartext Transmission of Sensitive Information. CWE-295 Improper Certificate Validation. CWE-297 Improper Validation of Certificate with Host Mismatch.

MASVS-NETWORK-2

The app performs identity pinning for all remote endpoints under the developer's control.

MASVS-NETWORK-1 requires TLS and real certificate checks. This control goes further for hosts the developer operates: the app trusts only specific certificates or public keys, not every root the device trusts. That practice is certificate pinning or public-key pinning.

No current androidsec rule maps to this id. Cleartext, missing network security config, and trust-all clients are MASVS-NETWORK-1.

Security controls and focus areas

  • Pins on the public key of the server certificate, with at least one backup pin.
  • Pins only for endpoints the developer controls. Public certificate authorities for the rest of the internet stay as they are.
  • A pin failure that aborts the connection. A failure that falls back to “trust any certificate” removes the control.

Common vulnerabilities and attacks

  • Certificate pinning bypass: a runtime hook makes the pin check return success so a proxy certificate is accepted.
  • Pins that are not actually checked, or that pin a certificate authority so broad that an attacker certificate still chains.
  • No pinning at all. That misses this control. It is not, by itself, a failure of MASVS-NETWORK-1 if TLS is otherwise correct.

How these issues are usually exploited

The person who controls the device, or a process that can inject code into the app, changes the pinning method so every certificate passes. Traffic to the pinned host can then be decrypted by a local proxy. Without that bypass, a private certificate authority added to the device is not enough, which is the point of the control.

OWASP Mobile Top 10 (2024)M5 Insecure Communication.
Typical severityInfo to Medium when pinning is simply absent and TLS is otherwise sound. High when a bypass, combined with a weak trust decision, exposes credentials on a network the attacker can observe.
Suggested CVSS rangeMissing pins are often unscored, or about 3.0–5.0, because the device trust store still has to be attacked. A bypass that lets a proxy read credentials is about 7.0–8.5 and depends on network position.
Common CWEsCWE-295 Improper Certificate Validation. CWE-296 Improper Following of a Certificate's Chain of Trust.

MASVS-PLATFORM-1

The app uses IPC mechanisms securely.

Android apps expose data and actions through activities, services, broadcast receivers, and content providers. Other apps, and sometimes a web page, can call those components. This control requires every one of those entry points to check who is calling and to treat the supplied data as untrusted.

androidsec maps exported components, implicit broadcasts that carry credentials, nested intent redirects, a FileProvider root-path, and a boolean intent extra that gates a screen to this control.

Security controls and focus areas

  • Explicit android:exported on every component, with exported left false unless another app must call it.
  • Custom permissions on exported components that handle sensitive data or actions.
  • Validation of intent extras, URI paths, and provider selection clauses before they are used.
  • Pending intents that are explicit and immutable.
  • Dangerous permissions requested only for a function the user can see and understand.

Common vulnerabilities and attacks

  • Exported activities, services, or receivers with no permission, so any app can start them.
  • Exported content providers that allow unauthenticated query, insert, update, or delete.
  • SQL injection through a provider selection or sortOrder argument.
  • Intent injection and intent redirection, where attacker-controlled extras change which component runs or which account is used.
  • Implicit intents that carry credentials or session tokens and can be received by another app.
  • Over-broad permissions (SMS, contacts, storage, location) that expand the impact of any later bug.

How these issues are usually exploited

A second app on the device, or an adb caller in a lab, starts the exported component or queries its provider URI. If the provider builds SQL from the caller’s selection string, a UNION query can return rows the app never intended to expose, including usernames it recorded. An exported activity that trusts an extra can open a screen that should have required login.

OWASP Mobile Top 10 (2024)M8 Security Misconfiguration. M4 Insufficient Input/Output Validation when intent or provider input is used unsafely. M1 Improper Credential Usage when the component returns or accepts credentials.
Typical severityInfo to Critical. A declared permission with no demonstrated leak is often Medium or Info. An exported provider that returns account data with no permission is High or Critical.
Suggested CVSS range3.1–9.8. Local-only access to an exported provider is commonly about 5.5–7.5. A browsable activity that a website can start, and that changes account state, sits at the top of the range.
Common CWEsCWE-926 Improper Export of Android Application Components. CWE-927 Use of Implicit Intent for Sensitive Communication. CWE-285 Improper Authorization. CWE-89 SQL Injection when the provider concatenates the selection.

MASVS-PLATFORM-2

The app uses WebViews securely.

WebViews render HTML inside the app. A page loaded there runs with the app’s identity on screen. This control requires that JavaScript, file access, and any bridge to native code are limited to content the app trusts.

androidsec maps JavaScript bridges, file and universal access, a WebView that loads a file:// URL or a URL taken from the user, and deep-link host checks to this control. A host check that uses endsWith("example.com") accepts evilexample.com.

Security controls and focus areas

  • JavaScript disabled unless the page needs it, and then only for known origins.
  • No addJavascriptInterface object that exposes app methods to page script. On older APIs that interface is reachable by any script in the page.
  • File URL access and universal file access left off, so a page cannot read the app’s files.
  • A WebViewClient that does not load arbitrary redirects, and that ignores untrusted javascript: and file: URLs.
  • WebView content loaded over HTTPS, or from the app’s own assets, rather than from shared storage.

Common vulnerabilities and attacks

  • JavaScript bridge: a page calls a Java object that was added for the WebView and reaches native functions.
  • Loading attacker-controlled HTML from external storage or from an intent extra, with JavaScript enabled.
  • File-scheme theft when setAllowUniversalAccessFromFileURLs or setAllowFileAccessFromFileURLs is on.
  • Trusted-UI spoofing: the banking chrome stays visible while the page content is replaced.

How these issues are usually exploited

The attacker writes an HTML file the WebView will load, or points the view at a URL they control. Script then runs inside the app. If a JavaScript interface is registered, the script calls those methods. If it is not, the result is still script execution and a forged screen, which is serious, but it is not native code execution. On current Android versions the file-access defaults block a page from reading other files unless the app turns those settings on.

OWASP Mobile Top 10 (2024)M8 Security Misconfiguration. M4 Insufficient Input/Output Validation for script injection into the WebView. M1 Improper Credential Usage if the bridge or the page can read stored credentials.
Typical severityMedium to Critical. Content injection with JavaScript and no native bridge is often High. A bridge that reaches file, token, or account methods is Critical.
Suggested CVSS range6.0–9.0 for a bridge into native code. About 5.0–7.0 when the impact is a forged screen and script that cannot leave the WebView.
Common CWEsCWE-749 Exposed Dangerous Method or Function. CWE-79 Improper Neutralization of Input During Web Page Generation. CWE-829 Inclusion of Functionality from Untrusted Control Sphere.

MASVS-PLATFORM-3

The app uses the user interface securely.

Passwords, card numbers, and one-time codes have to appear on screen sometimes. This control is about that moment: the platform must not keep a screenshot, a notification, or an overlay that another person or another app can read.

No current androidsec rule maps to this id.

Security controls and focus areas

  • FLAG_SECURE on screens that show secrets, so recents and screenshots do not capture them.
  • Masked password fields, and no secret echoed into a notification, a toast, or an accessibility announcement that is broader than it needs to be.
  • Tapjacking protection (filterTouchesWhenObscured) on controls that confirm a payment or a permission.

Common vulnerabilities and attacks

  • A one-time code or a full card number left in the overview screenshot or the notification shade.
  • An overlay drawn by another app that covers a trusted button and records the tap.
  • Shoulder surfing of an unmasked secret on a shared device.

How these issues are usually exploited

Someone with the unlocked device opens the recents list or the notification shade and reads the secret the app just displayed. Or a malicious app draws a transparent layer over the confirmation button and captures the moment the user taps. The app’s network security is irrelevant because the data was shown in the clear.

OWASP Mobile Top 10 (2024)M6 Inadequate Privacy Controls. M1 Improper Credential Usage when the displayed value is a password or one-time code. M8 Security Misconfiguration for a missing window flag.
Typical severityLow to High. A card number or one-time code in a screenshot or notification is High. A masked field that is briefly visible is Low.
Suggested CVSS range3.0–6.5. Access is local and usually needs the device in hand.
Common CWEsCWE-359 Exposure of Private Personal Information. CWE-200 Exposure of Sensitive Information. CWE-1021 Improper Restriction of Rendered UI Layers.

MASVS-CODE-1

The app requires an up-to-date platform version.

Each Android release fixes platform bugs and changes defaults: exported components, cleartext traffic, file access, and WebView behavior among them. An app that still allows very old versions keeps those old weaknesses available.

No current androidsec rule maps to this id. A low targetSdkVersion is mapped to MASVS-PLATFORM-1, because that old target changes how the platform treats components and permissions. The underlying issue is the one this control describes.

Security controls and focus areas

  • A targetSdkVersion on a current API level, so current platform security defaults apply.
  • A minSdkVersion high enough that known-broken platform versions are refused.
  • Features that need a new security API guarded so they are not silently skipped on older devices.

Common vulnerabilities and attacks

  • Pre-Android 12 export defaults, where a component with an intent filter is exported unless the app says otherwise.
  • Cleartext allowed by default on older targets that have no network security config.
  • WebView and file-sharing behaviors that were tightened only for apps that target a newer SDK.

How these issues are usually exploited

The attacker uses the older platform rule. A component the developer thought was private is still callable. Or cleartext is still permitted, and a network attacker reads traffic the developer assumed the OS would block. The exploit is the one that the newer default would have closed.

OWASP Mobile Top 10 (2024)M8 Security Misconfiguration.
Typical severityMedium to High. The score follows the platform behavior that stays enabled, not the version number by itself.
Suggested CVSS range4.0–7.5, matching the concrete weakness the old target leaves open.
Common CWEsCWE-477 Use of Obsolete Function. CWE-1188 Insecure Default Initialization of Resource.

MASVS-CODE-2

The app has a mechanism for enforcing app updates.

A critical bug can ship in a build that users keep installed. This control asks for a way to stop that build: a server that refuses old version codes, or a store update flow the app cannot skip.

No current androidsec rule maps to this id.

Security controls and focus areas

  • The service rejects clients below a minimum version for sensitive calls.
  • A user-visible update path, including Play in-app updates or an equivalent, that blocks the app until the new build is installed.
  • Version checks that the server performs. A check that exists only inside the old binary can be removed with the bug.

Common vulnerabilities and attacks

  • No minimum version. Users stay on a build with a known authentication or crypto flaw.
  • A client-side “please update” dialog with a skip button, and a server that still accepts the old client.

How these issues are usually exploited

The attacker uses the public details of a flaw in an old version. Because the server still talks to that version, the flaw remains reachable after a fix has been published. The attack is whatever the old bug allowed.

OWASP Mobile Top 10 (2024)M8 Security Misconfiguration.
Typical severityInfo to Medium on its own. High when a specific fixed vulnerability is still exploitable because old clients are accepted.

MASVS-CODE-3

The app only uses software components without known vulnerabilities.

A full review of every library is not always possible during a test. This control is the part that is visible from the outside: dependencies with a published vulnerability, identified by name and version.

No current androidsec rule maps to this id.

Security controls and focus areas

  • Libraries and SDKs kept on versions that are not in a known-vulnerability feed.
  • A build that records dependency versions so a later advisory can be matched.
  • Native code and bundled WebView or TLS stacks included in that inventory, not only Java dependencies.

Common vulnerabilities and attacks

  • An old networking, parsing, or image library with a published remote or local bug.
  • A copied SDK that the app never updates, including one nested inside another SDK.

How these issues are usually exploited

The attacker matches the library version in the APK to a public advisory and uses that advisory’s method against the app. The impact is the impact of the advisory: a parser crash, a TLS bypass, or code execution inside the app process.

OWASP Mobile Top 10 (2024)M2 Inadequate Supply Chain Security.
Typical severityLow to Critical, taken from the vulnerability in the component and from whether the app actually calls the affected code.
Suggested CVSS rangeUse the advisory’s CVSS, commonly 4.0–9.8, and lower it when the vulnerable function is not reachable from the app.
Common CWEsCWE-1104 Use of Unmaintained Third Party Components. CWE-1395 Dependency on Vulnerable Third-Party Component. The specific bug inside the library has its own CWE.

MASVS-CODE-4

The app validates and sanitizes all untrusted inputs.

Data arrives from the UI, from other apps, from the network, and from files. Any of it may have been changed by someone else. The app has to treat it as untrusted before it reaches a query, a path, a script, or a parser. This is what stops SQL injection, script injection, path traversal, and insecure deserialization.

androidsec maps a runtime crash on unexpected input to this control. A crash is a signal that the input was not handled. It is not, by itself, proof of injection.

Security controls and focus areas

  • Query parameters bound, not concatenated, for SQL and similar stores.
  • Paths, URIs, and intent extras checked against an allow-list before use.
  • Structured data parsed with a safe parser, and deserialization limited to types the app expects.
  • WebView and deep-link parameters encoded before they are placed into HTML or a URL.

Common vulnerabilities and attacks

  • SQL injection through a content-provider selection, a search box, or a deep-link parameter. A provider that forwards the caller’s selection into SQLite is this case.
  • DexClassLoader or loadClass running an APK, a DEX, or another app’s classes that the user or a second app can replace.
  • Path traversal that reads a file outside the directory the app meant to open.
  • Script injection when a parameter is written into a WebView or a local HTML page.
  • Insecure deserialization of an object graph the attacker supplied.
  • A crash on a malformed extra or response, which shows the failure path was not handled.

How these issues are usually exploited

The attacker sends the unexpected value through whichever door accepts it: an intent extra, a link, a file name, or a server response the app trusts. If that value is glued into a query, the query returns extra rows. If it is glued into a path or a page, the app reads the wrong file or runs the supplied script. A crash is the weak form of the same mistake: the app did not define what should happen, and the process died instead.

OWASP Mobile Top 10 (2024)M4 Insufficient Input/Output Validation.
Typical severityMedium to Critical. Injection that reads or changes other users’ data is Critical. A crash with no further impact is Medium or Low.
Suggested CVSS range5.0–9.8. Remote injection into a query or a deserializer sits at the top. A local deep link that only crashes the app is near the bottom.
Common CWEsCWE-20 Improper Input Validation. CWE-89 SQL Injection. CWE-79 Improper Neutralization of Input During Web Page Generation. CWE-22 Path Traversal. CWE-502 Deserialization of Untrusted Data.

MASVS-RESILIENCE-1

The app validates the integrity of the platform.

Secure storage, biometrics, and the app sandbox assume the operating system has not been modified. This control asks the app to notice a compromised device: root, a custom image, an unlocked bootloader, or a failed device-integrity attestation. OWASP is explicit that the absence of this kind of check is not, by itself, a vulnerability. It is extra protection for a specific threat model. The rest of MASVS still has to hold.

Security controls and focus areas

  • Play Integrity, or an equivalent attestation, verified on the server rather than only inside the app.
  • Local signals used as a hint: unexpected superuser binaries, test keys, ro.debuggable, known hook frameworks.
  • A response that matches the risk. A payment or a fresh token can be refused. A label that only says the device is rooted does not protect data.

Common vulnerabilities and attacks

  • Root detection that looks for a file path or the su binary and can be hidden by renaming files or by a runtime hook.
  • Root-detection bypass that flips the Boolean the app checks, while the real device stays privileged.
  • Emulator and debugger checks that are equally local and equally visible to the person running the app.
  • Treating “no root check” as if it were the same bug as an exported component or a hardcoded key. It is not. The finding is informational unless the check is the only gate on a sensitive action.

How these issues are usually exploited

On a device the tester controls, the check is observed and then hidden: the file it looks for is absent from that path, or the method that returns the result is changed in memory. If the app only updates a text label, nothing further happens. If the same check is what allows a transfer or the release of a key, bypassing it reaches that function. The useful fix is to keep secrets and decisions on the server, and to verify device integrity there.

OWASP Mobile Top 10 (2024)M7 Insufficient Binary Protections.
Typical severityInfo to Low for “a root check exists” or “no root check exists”. Higher only when the check is the sole control in front of a sensitive operation, and then the severity follows that operation.
Suggested CVSS rangeUsually unscored, or 0.0–3.0. A bypass that is the only gate on a sensitive function is scored with the impact of that function, not as a generic root finding.
Common CWEsCWE-693 Protection Mechanism Failure. There is often no weakness CWE for the mere presence of a client-side check.

MASVS-RESILIENCE-2

The app implements anti-tampering mechanisms.

The app runs on a device the user controls, so a modified package is easy to install. This control tries to detect changes to the original code and resources: signature checks, installer checks, and detection of a repackaged binary. As with the rest of resilience, missing these checks is additional risk for cheating, cloning, or a backdoored republish. It is not automatically a vulnerability.

This project also files android:debuggable="true" under this control. A debug build is a related client-side weakness: a debugger, or run-as, can read the app’s private files and change its behavior without root. That is active debug code left in the package. It is not the same thing as a missing signature check, and the explanation below keeps the two apart.

Security controls and focus areas

  • Release builds with android:debuggable="false" and no debug logging of secrets.
  • Verification of the app’s signing certificate against the expected value, with the decision enforced somewhere the modified app cannot simply skip.
  • Detection of repackaging, attached debuggers, and instrumentation, used to protect specific business logic rather than as the only security control.
  • Server-side checks that do not trust a client that claims to be unmodified.

Common vulnerabilities and attacks

  • A release package that is still debuggable, so private storage can be read as the app user.
  • Tamper checks that compare a value inside the same binary the attacker is editing, and that therefore disappear in a rebuild.
  • Repackaging: the app is decoded, a method is patched, and the package is signed with a new key and installed.
  • Runtime patching of the check so the original package never has to be rebuilt.

How these issues are usually exploited

For a debuggable package, a local user runs as the app and reads private preferences, databases, and files that the sandbox would otherwise hide. For a tamper check, the attacker either edits the method that performs the check and reinstalls the package, or changes the method’s result while the process is running. If the server still requires its own authentication, the modified client does not gain an account. If the check was the only thing standing in front of a local premium feature or a locally stored key, the modified client gets that feature or that key.

OWASP Mobile Top 10 (2024)M7 Insufficient Binary Protections for missing or bypassed tamper checks. M8 Security Misconfiguration for a package shipped with debugging enabled.
Typical severityInfo when the observation is only that no tamper check exists. High when a build that stores secrets is debuggable, because private data is then readable without root.
Suggested CVSS rangeMissing tamper checks are often unscored. A debuggable build that exposes stored credentials to a local user is commonly about 5.0–7.5, depending on what those files contain.
Common CWEsCWE-489 Active Debug Code. CWE-693 Protection Mechanism Failure. CWE-354 Improper Validation of Integrity Check Value.

MASVS-RESILIENCE-3

The app implements anti-static analysis mechanisms.

Reading the app is usually the first step toward changing it. This control tries to make that reading slower: obfuscation, removal of readable names, and protection of string constants. OWASP is explicit that missing resilience measures are not vulnerabilities. They are extra layers for a threat model that needs them. The rest of MASVS still applies.

androidsec maps the presence of Frida, Xposed, debugger, and emulator checks to this id. Those checks are runtime signals, and the official home for anti-instrumentation is MASVS-RESILIENCE-4. In this project they are informational observations that some resilience code exists. Seeing the check is not a finding that the app is weak, and not seeing obfuscation is not the same kind of bug as an exported component.

Security controls and focus areas

  • Release builds run through an obfuscator so class and method names are not a map of the business logic.
  • Strings that would otherwise name secrets, keys, or check locations are not left in plaintext in the binary.
  • Debug symbols and logging stripped from the release package.

Common vulnerabilities and attacks

  • A release build that decompiles to readable logic, including the location of keys and of security checks.
  • String extraction that recovers a key or a URL without fully understanding the code.
  • Treating “no obfuscation” as if it disclosed data by itself. The disclosure still requires a secret to have been stored in the program.

How these issues are usually exploited

The package is decompiled and read. Names and strings point at the crypto helper, the password check, or the root check. That reading then feeds a real bug elsewhere: a hardcoded key, a Boolean check, or a trust decision. Obfuscation slows the reading. It does not fix the bug the reading finds.

OWASP Mobile Top 10 (2024)M7 Insufficient Binary Protections.
Typical severityInfo. Raise it only when the readable binary is what exposes a secret or a check that is the sole gate on a sensitive action, and then score that secret or that gate.
Suggested CVSS rangeUsually unscored, or 0.0–3.0. Missing obfuscation is not given a high score on its own.
Common CWEsCWE-693 Protection Mechanism Failure when a check meant to hinder analysis is bypassed. Missing obfuscation is not, by itself, a weakness CWE.

MASVS-RESILIENCE-4

The app implements anti-dynamic analysis techniques.

Static reading is often paired with running the app under a debugger, a tracer, or an instrumentation toolkit. This control tries to detect that and to stop the process from being changed while it runs. As with the other resilience controls, its absence is not a vulnerability.

No current androidsec rule maps to this id. Observations that a Frida, Xposed, debug, or emulator check exists are filed under MASVS-RESILIENCE-3.

Security controls and focus areas

  • Detection of a debugger, of common instrumentation frameworks, and of a modified runtime, with the result checked somewhere the same process cannot simply skip.
  • Server-side signals, such as an attestation result, used for decisions that matter.
  • No reliance on a single local Boolean as the only protection for a key or a payment.

Common vulnerabilities and attacks

  • A debugger or instrumentation check that looks for one process name or one file path.
  • A runtime hook that forces the check to report “clean” while the hook remains in place.
  • An emulator check used as if a passed check proved the user is the real customer.

How these issues are usually exploited

The app is started under the tool it hoped to see, and the method that reports the tool is changed to report nothing. Traces and hooks then follow the login, the crypto call, or the certificate check. If those other controls are sound, the session still cannot be forged. If a local Boolean was the only gate, the hook removes it.

OWASP Mobile Top 10 (2024)M7 Insufficient Binary Protections.
Typical severityInfo to Low for a missing or bypassed local check. Higher only when that check is the only control in front of a sensitive operation.
Suggested CVSS rangeUsually unscored, or 0.0–3.0. Score the operation behind the check when the check is its only gate.
Common CWEsCWE-693 Protection Mechanism Failure.

MASVS-PRIVACY-1

The app minimizes access to sensitive data and resources.

The app should request only the data its function needs, and only after the user has agreed. Third-party SDKs are part of the app for this purpose: they must not collect before consent or ignore a refusal. Passing data down a chain of SDKs the developer did not review is in scope.

No current androidsec rule maps to this id. Broad dangerous permissions are mapped to MASVS-PLATFORM-1, because that is how the platform exposes the capability. The privacy question is whether the app needed the data at all.

Security controls and focus areas

  • Permissions and data fields limited to what the current feature uses.
  • Consent collected before an SDK starts, and honored by that SDK.
  • No onward sharing with another app or another SDK beyond what the user was told.

Common vulnerabilities and attacks

  • An SDK that collects identifiers or location before the consent dialog, or after the user refuses.
  • A permission requested “just in case”, which widens the damage of any later bug.
  • Data handed to a library that sends it to its own backend.

How these issues are usually exploited

The collection does not need a further break-in. The app, or an SDK inside it, sends the data because that is what the code does. Traffic or the SDK’s configuration shows identifiers, contacts, or location leaving the device for a purpose the user did not accept. A later vulnerability then has more data available than the feature required.

OWASP Mobile Top 10 (2024)M6 Inadequate Privacy Controls. M2 Inadequate Supply Chain Security when the collector is a third-party SDK.
Typical severityLow to High. Covert collection of location, contacts, or identifiers is High. A permission that is declared and never used is Low or Info.
Suggested CVSS range3.0–7.0. Privacy impact is real and the “attack” is often the app’s own network call, so complexity is low once the behavior is confirmed.
Common CWEsCWE-359 Exposure of Private Personal Information. CWE-200 Exposure of Sensitive Information.

MASVS-PRIVACY-2

The app prevents identification of the user.

Users should not be re-identified across purposes by a stable fingerprint. Data can be aggregated, anonymized, or pseudonymized. A signal collected for fraud detection must not be reused, unchanged, for advertising.

No current androidsec rule maps to this id.

Security controls and focus areas

  • No long-lived device identifier sent where a rotating or purpose-bound id would do.
  • Separate identifiers for fraud, support, and measurement, so one stream cannot be joined to another.
  • Advertising identifiers used only where the platform’s limit-ad-tracking setting is honored.

Common vulnerabilities and attacks

  • A hardware or advertising id combined with behavior and shared with an analytics or ads SDK.
  • The same pseudonym used for two purposes, which makes the user linkable.
  • IP address plus device properties used as a fingerprint after the user resets the advertising id.

How these issues are usually exploited

The observer does not break the account. They join records. The identifier in the app’s traffic matches an identifier in another data set, and activity that was supposed to be separate becomes one profile. Resetting a single id does not help when the app still sends the other signals.

OWASP Mobile Top 10 (2024)M6 Inadequate Privacy Controls.
Typical severityLow to Medium. High only when the identifier is tied to sensitive categories of data the user did not expect to be linked.
Suggested CVSS range3.0–5.5. This is a privacy failure more often than a classic compromise of an account.
Common CWEsCWE-359 Exposure of Private Personal Information.

MASVS-PRIVACY-3

The app is transparent about data collection and usage.

Users have to be able to learn what is collected, where it goes, and which of that behavior they would not expect. Store disclosures and the in-app policy have to match the traffic. Background collection is part of the disclosure, not an exception.

No current androidsec rule maps to this id.

Security controls and focus areas

  • A privacy policy and a store data-safety form that list the data the app and its SDKs actually send.
  • Notice before behavior a user would not expect, including collection while the app is in the background.
  • Updates to that notice when a new SDK or a new field is added.

Common vulnerabilities and attacks

  • Traffic shows identifiers, location, or contacts that the policy and the store form do not mention.
  • An SDK named nowhere in the disclosure that receives a copy of the user’s data.
  • Collection that starts before the policy is shown.

How these issues are usually exploited

There is often no second attacker. The app’s own requests are compared with its own notice. Fields that appear on the wire and not in the notice are the finding. The harm is that the user could not refuse a practice they were not told about.

OWASP Mobile Top 10 (2024)M6 Inadequate Privacy Controls.
Typical severityInfo to Medium. Medium when the undisclosed data is contact, location, or a stable identifier. Info when the gap is wording and the data is already described.
Suggested CVSS rangeOften unscored. About 2.0–5.0 when undisclosed personal data leaves the device.
Common CWEsCWE-359 Exposure of Private Personal Information.

MASVS-PRIVACY-4

The app offers user control over their data.

Consent is not a one-time switch. The user needs a way to change their mind, to delete or export what was collected, and to see a new prompt when the app starts wanting more than it asked for originally.

No current androidsec rule maps to this id.

Security controls and focus areas

  • In-app controls to withdraw consent, delete an account, and change privacy choices.
  • Deletion that reaches the app’s own server and the SDKs that received a copy, as far as the app can require it.
  • A fresh prompt when a release collects a new category of data.

Common vulnerabilities and attacks

  • No deletion path, or a path that hides the account in the UI and leaves it on the server.
  • A consent refusal that the SDK ignores.
  • A later release that collects more data under the old consent.

How these issues are usually exploited

The user refuses or deletes, and the previous identifier keeps working. Requests after the refusal still carry the data. Or support has no way to remove the account, so a copy remains after the user believes it is gone. The failure is the missing control, observed by repeating the action and watching the traffic.

OWASP Mobile Top 10 (2024)M6 Inadequate Privacy Controls.
Typical severityLow to Medium. Medium when deletion or withdrawal is promised and then does not happen for personal data.
Suggested CVSS range2.0–5.0. This is scored as a privacy-control failure, not as remote code execution.
Common CWEsCWE-359 Exposure of Private Personal Information.
